## How the home-lab test environment works

Real **Chromium 151**, **Firefox 153** and **WebKit 26.5** ran in separate Linux network namespaces, each behind its own router namespace with a Linux kernel NAT profile, using fake cameras and microphones. The gate ran on a simulated internet. Desktop gateways and host nodes ran next to their peers. This setup exercises controlled, repeatable network profiles; it does not reproduce the full behavior or variability of real routers and internet providers. Every run asserts:

- the path that **each side** of every pair reports;
- that media actually flows: more than 50 audio packets and more than 30 decoded video frames per origin peer;
- that the gate's traffic stays signalling-sized.

| Profile | Emulates |
|---|---|
| `eim` | A home router: endpoint-independent mapping, port-restricted filtering |
| `random` | A hard NAT: symmetric, a fully random port for every destination |
| `udpblock` | A firewall that drops all UDP |
| `upnp` | A home router running miniupnpd 2.3.4 with PCP, NAT-PMP and UPnP IGD |
| `public` | No NAT: a public address |
| `gateonly` | A network that only forwards TCP to and from the gate host |
| `v6` | IPv6 behind a stateful firewall, with IPv4 UDP blocked |

**Total: 40 of 40 home-lab network runs passed, 0 failed.** The cross-engine runs put Firefox and WebKit behind the simulated hard profiles, and use Chromium only where a third party is needed.

### What this answers

Earlier research that only tried direct routes proved its own boundary: two fully random symmetric NATs connected in 0 of 3 attempts, and UDP-blocked peers had no route at all. In these simulated network tests Freehop connects both cases, through a desktop participant's gateway, the session's host node or a participant. The same test setup leaves a hard-NAT pair without a helper unreachable. A network profile that reaches nothing but the gate (`gate-only`) remains unreachable even with session helpers. There, media is impossible without the operator carrying it, and Freehop reports `unreachable`.

## Other evidence

### Unit tests: 156 of 156

- STUN codec with the RFC 5769 test vectors, plus fuzzing.
- TURN server: integrity, framing, quotas, room bandwidth, IPv6 destination policy and TCP deadlines.
- Port mapper: 30 cases against simulated PCP, NAT-PMP and UPnP routers.
- Gate: routing, isolation, floods, tokens, capacity, STUN, keepalive and proxy trust.
- Gateway: bounded room-scoped credentials, revocation retention, renderer isolation and loopback refusal.
- Protocol regressions: gate audiences, STUN pinning, discovery churn, both-endpoint forwarding consent and cancellation, key rotation and copied aliases.

### TURN conformance-tool run (part of the original home-lab test run)

coturn's `turnutils_uclient` against Freehop's TURN server: **UDP 800/800 and TCP 800/800 messages, 0 lost.** It runs in Send/Data mode, because coturn's client uses obsolete RFC 5766 channel numbers. ChannelData is covered by the browser tests.

### TURN browser interop (macOS, original test run)

20 passed, 0 failed, 6 blocked. All six blocked cases are WebKit over TCP, caused by a TURN URL bug in Playwright's WebKit build (WebKit bug 320931). The client detects it and degrades to UDP TURN for that engine.

### Local browser suites (macOS)

The original local test run included every suite below. After the security fixes, the three-engine TLS mesh, multi-gate outage, kick/rekey and SDK reference app suites were rerun. Public tracker connectivity was also exercised in the live demo checks.

- A mesh of three Chromium browsers.
- Chromium, Firefox and WebKit in one mesh over TLS.
- Multi-gate: peers on disjoint gates introduced through the mesh, then **every gate shut down while media continued** (about 600 audio packets per peer in 6 seconds).
- Kick and rekey.
- **A public WebTorrent tracker as the only gate** (`wss://tracker.openwebtorrent.com`): no server of our own.
- The SDK reference app driven through its own interface and API, including a kick rotation.

### Security review

The earlier source and test review recorded 11 findings. The subsequent source review and security regressions cover key epochs, alias revocation, tickets, authority races, forwarding authorization, gate input limits, UDP response budgets and Electron IPC. See the [security model](./concepts/security.mdx) for the current trust limits.

## Not yet verified

1. **Physical networks:** real home routers, 4G and 5G carrier NAT (usually with IPv6), a UDP-blocking corporate network, and routers without UPnP, PCP or NAT-PMP.
2. **The [Redline Wars](./redline-wars.mdx) integration** through the SDK, with the game as test environment, including its strict frame-time gates with voice on.
3. **iOS Safari and Android browsers.** Only desktop engines were tested.
4. **Media quality under real load.** Forwarded (bridged) media is re-encoded by the participant, and the upstream budget of a forwarding participant on home broadband is still unmeasured.

## Reproduce

```bash
node --test test/*.test.mjs
node test/browser/smoke.mjs chromium,firefox,webkit --tls
node test/browser/multigate.mjs && node test/browser/rekey.mjs && node test/browser/tracker.mjs && node test/browser/example-app.mjs
```

The home-lab NAT test harness builds network namespaces and kernel NAT rules, so its scripts refuse to run anywhere except a disposable, privileged Linux container (`FREEHOP_DISPOSABLE_LAB=yes`, as root):

```bash
docker run -d --name freehop-lab --privileged -v "$PWD":/work mcr.microsoft.com/playwright:v1.62.0-noble sleep infinity
docker exec freehop-lab bash -lc 'apt-get update && apt-get install -y iproute2 iptables miniupnpd coturn openssl'
docker exec -e FREEHOP_DISPOSABLE_LAB=yes freehop-lab bash -lc 'cd /work && lab/qualify.sh'
```

Every run writes a JSON report with the source hashes, paths, media counters and gate statistics.
